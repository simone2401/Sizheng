# 课程思政模型服务接口内部设计文档 V1\.0

整体接口任务总结：

> 本项目中，模型服务侧负责提供统一 AI 对话接口能力。上游平台仅传递用户请求、业务类型（chatType）及必要的教材/案例等上下文信息；模型接口服务接收到请求后，根据 metadata 中的信息完成业务路由，并在接口内部完成静态资源检索、知识组装、安全控制、Prompt 构造等流程，将教材内容、知识点、课程思政资源等上下文注入模型请求后调用大模型生成结果。案例导引场景由上游直接提供案例内容，模型侧主要负责对话引导；备课助手场景由模型侧根据教材章节、知识点等信息从静态 JSON 资源中检索相关内容并组装。模型服务保持无状态，不存储 conversation history，仅透传和记录 conversationId、turnId 等链路字段；最终通过统一流式/非流式响应协议返回模型生成内容，同时补充 outputType、usage、error 等标准字段。
> 
> 

**文档定位：模型服务内部技术设计文档**
**对外统一接口：** `POST /v1/chat/teaching`
**业务区分方式：** `metadata.chatType`
**静态资源：** 教材结构化 JSON
**服务状态：** 无状态，不保存 `conversation history`
**安全策略：** 以外生安全围栏为主，从输入 Prompt 控制和输出 Token 拦截开始建设

---

# 一、总体设计

## 1\.1 设计目标

课程思政模型服务面向上游教学平台提供统一 AI 对话能力。所有 AI 对话统一调用 POST /v1/chat/teaching，通过 metadata\.chatType 区分不同业务场景。

当前支持：

模型服务收到请求后，根据业务类型进入对应业务处理链。业务处理链负责读取请求中的用户输入和业务元数据，并按业务需要查询教材静态资源、组装教学上下文、构造对应 Prompt、执行安全控制，最终调用大模型并按照统一协议返回结果。

模型服务本身保持无状态，不保存用户历史对话。`conversationId` 和 `turnId` 仅用于请求链路标识和结果关联；如需要多轮上下文，由上游平台通过 `messages` 传入。当前对外接口已经明确采用这一原则。

整体架构不是“所有业务经过同一套 Prompt 流程”，而是：

```Plain Text
上游教学平台
                               │
                               │ POST /v1/chat/teaching
                               ▼
                    ┌─────────────────────┐
                    │ TeachingChatService │
                    └──────────┬──────────┘
                               │
                       Request Validation
                               │
                         chatType 路由
                               │
              ┌────────────────┴────────────────┐
              │                                 │
              ▼                                 ▼
      case_guide_study                 lesson_plan_assist
              │                                 │
              ▼                                 ▼
         案例导引业务链                      备课助手业务链
              │                                 │
       ┌──────┴──────┐                    ┌─────┴─────┐
       │             │                    │           │
       ▼             ▼                    ▼           ▼
    案例内容      教材资源查询          教材资源查询   用户/原教案
       │             │                    │           │
       └──────┬──────┘                    └─────┬─────┘
              ▼                                 ▼
       Case Context                       Lesson Context
              │                                 │
              ▼                                 ▼
    Case Prompt Builder               Lesson Prompt Builder
              │                                 │
              └──────────────┬──────────────────┘
                             ▼
                     Safety Control
                             │
                             ▼
                        Model Client
                             │
                             ▼
                     Response Formatter
                             │
                             ▼
                          平台
```

这里需要特别明确：

> **两个业务链在“业务处理、资源选择、Context 组装、Prompt 构造”阶段保持独立；仅在底层资源查询能力、模型调用、安全控制和响应封装等公共基础能力上复用组件。**
> 
>

# 三、静态资源与资源查询层

## 3\.1 静态资源定位

当前教材数据已经形成结构化 JSON，不需要模型服务自行重新解析 Excel。

主要数据包括：

```Plain Text
entities.json
- `json_output/PEP8U_PHYSICS/raw_sheets/*.json`：按 Excel 分表逐个导出的原始 JSON。
- `json_output/PEP8U_PHYSICS/entities.json`：实体集合（教材、章节、节、知识点等）。
- `json_output/PEP8U_PHYSICS/relations.json`：关系集合（章节-节、节-知识点、段落-标签等）。
- `json_output/PEP8U_PHYSICS/summary.json`：总览统计（分表数量、实体数量、关系数量）。
- `json_output/PEP8U_PHYSICS/graph.json`：实体+关系+统计的统一视图。
- `json_output/PEP8U_PHYSICS/marble/`：对齐 os-taxonomy 风格的图谱文件（`topics.json`、`dependencies.json`、`curriculum-standards.json`、`clusters.json`、`manifest.json`）。
```

其中 `entities.json` 是主要实体集合，包含：

```Plain Text
textbook
chapters
sections
curriculum_standards
knowledge_points
textbook_chunks
ideology_paragraphs
ideology_tags
```

例如：

- `knowledge_points` 包含 `knowledge_point_id`、`section_id`、`title`、`summary`、`cognitive_level` 等字段；

- `textbook_chunks` 包含 `chunk_id`、`section_id`、`page`、`text`；

- `ideology_paragraphs` 包含 `paragraph_id`、`section_id`、`textbook_original_excerpt`、`ideology_l3_codes`、`ideology_l3_labels` 等字段。

`relations.json` 用于描述实体之间的关联，包括：

```Plain Text
chapter_has_section
section_has_standard
section_has_knowledge_point
section_has_chunk
section_has_ideology_paragraph
tag_l1_has_l2
tag_l2_has_l3
paragraph_tagged_with_l3
```

因此，静态资源查询不能简单理解成“根据关键词读取一个 JSON 文件”，而应该理解成：

> **根据教材定位信息和知识点信息，从实体和关系数据中定位当前教学场景所需要的教材内容、知识点、课标及思政资源。**
> 
> 

---

## 3\.2 静态资源查询接口

模型服务内部建议提供统一资源查询接口：

```HTTP
GET /v1/teaching/resources
```

查询参数与对外 `metadata` 保持对应：

这里的资源接口**不是给上游平台使用的业务接口**，而是模型服务内部的数据查询能力。

---

## 3\.3 静态资源接口不返回 Markdown

静态资源接口建议返回：

> **结构化 JSON 数据，而不是已经拼接好的 Markdown。**
> 
> 

例如查询某一节教材后，可以返回：

```JSON
{
  "dataVersion": "2026-08",
  "textbook": {},
  "chapter": {},
  "section": {},
  "knowledgePoints": [],
  "textbookChunks": [],
  "curriculumStandards": [],
  "ideologyParagraphs": [],
  "ideologyTags": {}
}
```

具体字段来自当前教材 JSON 的已有数据，而不是重新设计一套教材数据。

原因是资源查询和 Prompt 构造属于两个不同职责：

```Plain Text
静态资源接口：
“找到什么资源”

Context Builder：
“哪些资源对当前业务有用，以及如何组织”

Prompt Builder：
“如何把这些上下文交给模型”
```

如果静态资源接口直接返回 Markdown，就会把**数据层和业务 Prompt 层耦合**，后续案例导引和备课助手需要不同 Prompt 时会非常难维护。

# 四、案例导引学习业务链

## 4\.1 业务定义

```Plain Text
chatType = case_guide_study
```

案例内容由上游平台通过 `messages` 提供；同时，当前接口已经要求平台提供学段、学科、教材版本、章节和小节，因此模型服务可以据此查询教材静态资源。

因此案例导引是：案例内容\+教材教学上下文 → 案例导引 Context → 案例导引 Prompt → 模型

---

## 4\.2 处理流程

```Plain Text
case_guide_study
        │
        ▼
读取 messages 中的案例内容
        │
        ▼
读取 metadata 教材定位信息
        │
        ▼
Case Resource Query
        │
        ▼
查询：
教材
章节/节
知识点
教材原文
相关思政段落/标签
        │
        ▼
Case Context Builder
        │
        ▼
Case Prompt Builder
        │
        ▼
Safety Control
        │
        ▼
ModelClient
```

案例导引的 Prompt 核心目标是基于案例和教材教学上下文进行苏格拉底式引导，而不是直接生成完整教案。

因此其 `outputType` 默认 chat\_text

# 五、课程思政备课助手业务链

## 5\.1 业务定义

```Plain Text
chatType = lesson_plan_assist
```

该业务统一承载教案生成、教案修改、课程思政融合，三者不再拆成三个接口。

上游平台在修改或融合场景下，将原教案内容拼接到 `messages` 中。

---

## 5\.2 处理流程

```Plain Text
lesson_plan_assist
        │
        ▼
读取 messages
（用户需求 / 原教案 / 修改要求）
        │
        ▼
读取 metadata
（教材 / 章节 / 小节 / 知识点）
        │
        ▼
Lesson Resource Query
        │
        ▼
查询：
教材原文
知识点
课标
思政段落
思政标签
        │
        ▼
Lesson Context Builder
        │
        ▼
Lesson Plan Prompt Builder
        │
        ▼
Safety Control
        │
        ▼
ModelClient
```

这里的 Prompt 与案例导引**明确不同**。

备课助手需要让模型：

```Plain Text
理解教材内容
+
理解知识点
+
结合课程思政资源
+
根据用户需求生成/修改教案
```

因此其输出通常为outputType = lesson\_plan\_markdown

当前对外接口已经定义了 `chat_text` 和 `lesson_plan_markdown` 两种输出类型。

# 六、两个业务如何复用能力

这里是之前架构图最容易产生误解的地方。

正确的关系应该是：

```Plain Text
TeachingChatService
                            │
                      chatType Router
                            │
              ┌─────────────┴─────────────┐
              │                           │
              ▼                           ▼
      CaseGuideHandler            LessonPlanAssistHandler
              │                           │
              ▼                           ▼
      Case Resource Query         Lesson Resource Query
              │                           │
              ▼                           ▼
      Case Context Builder        Lesson Context Builder
              │                           │
              ▼                           ▼
      Case Prompt Builder          Lesson Prompt Builder
              │                           │
              └────────────┬──────────────┘
                           │
                           ▼
                    SafetyGuard
                           │
                           ▼
                      ModelClient
                           │
                           ▼
                  ResponseFormatter
```

这里的：

```Plain Text
Case Resource Query
Lesson Resource Query
```

**不是同一个业务处理模块。**

但是它们底层可以调用同一个：

```Plain Text
ResourceQueryService
```

即：

```Plain Text
Case Resource Query
        │
        └──────► ResourceQueryService
                       │
                       ▼
                  JSON Repository


Lesson Resource Query
        │
        └──────► ResourceQueryService
                       │
                       ▼
                  JSON Repository
```

所以正确理解是：

> **业务层分开，底层能力复用。**
> 
> 

而不是：

> **业务分开以后又重新合成同一个业务流程。**
> 
>

# 八、安全控制

当前阶段采用外生安全围栏，不依赖模型本身已经成熟的内生安全能力。

整体位置：

```Plain Text
用户输入
    ↓
Input Safety Guard
    ↓
业务 Context
    ↓
Prompt Builder
    ↓
ModelClient
    ↓
Output Safety Guard
    ↓
Response
```

输入侧重点控制 Prompt Injection、恶意指令以及明显偏离业务的异常输入。

输出侧采用 Token/文本增量拦截机制。模型流式生成过程中，不直接将模型 Token 原样发送给上游，而是先经过输出安全检测：

```Plain Text
Model Token
    ↓
Output Safety Guard
    ↓
允许 → 返回 SSE
拦截 → 停止输出并返回 SAFETY_BLOCK
```

因此安全控制是两个业务共同复用的基础能力，但具体业务 Prompt 仍然保持独立。

# 九、模型调用与响应

业务层不直接依赖具体模型 SDK，而统一通过：

```Plain Text
ModelClient
```

调用模型。

```Plain Text
CaseGuideHandler
        │
LessonPlanAssistHandler
        │
        ▼
   ModelClient
        │
        ▼
   Model Service
```

模型调用完成后，由统一 `ResponseFormatter` 按对外协议封装。

响应一级字段保持：

```Plain Text
requestId
conversationId
turnId
model
outputType
content
finishReason
usage
error
```

其中：

- `conversationId`、`turnId` 不代表模型内部保存了会话；

- `usage` 用于 Token 使用统计；

- `outputType` 区分普通对话文本和教案 Markdown；

- `error` 统一描述异常。

当前对外接口已经明确流式 SSE 和非流式 JSON 两种返回模式。

# 十、静态资源模块内部实现

静态资源模块建议保持简单，不需要一开始就引入数据库或复杂检索系统。

当前 JSON 已经具备比较完整的实体和关系结构，因此 V1\.0 可以采用：

```Plain Text
StaticResourceService
        │
        ▼
ResourceQueryService
        │
        ▼
JSONRepository
        │
        ├── entities.json
        ├── relations.json
        ├── graph.json
        └── raw_sheets/*
```

其中 `JSONRepository` 启动时加载 JSON 并建立内存索引。

例如：

```Plain Text
section_id
    ↓
knowledge_points
textbook_chunks
ideology_paragraphs
curriculum_standards
```

关系依据 `relations.json` 中的：

```Plain Text
section_has_knowledge_point
section_has_chunk
section_has_ideology_paragraph
section_has_standard
```

进行关联。

这样查询过程就不需要每次遍历整个 JSON 文件。

# 十四、V1\.0 最终架构

整个系统最终可以概括为：

```Plain Text
┌──────────────────┐
                         │    上游教学平台    │
                         └────────┬─────────┘
                                  │
                                  ▼
                    POST /v1/chat/teaching
                                  │
                                  ▼
                         ┌────────────────┐
                         │  Chat Router   │
                         └───────┬────────┘
                                 │
                  ┌──────────────┴──────────────┐
                  │                             │
                  ▼                             ▼
          CaseGuideHandler             LessonPlanAssistHandler
                  │                             │
                  ▼                             ▼
        CaseResourceQuery              LessonResourceQuery
                  │                             │
                  └──────────────┬──────────────┘
                                 │
                         ResourceQueryService
                                 │
                                 ▼
                           教材 JSON 数据
                                 │
                  ┌──────────────┴──────────────┐
                  │                             │
                  ▼                             ▼
          CaseContextBuilder            LessonContextBuilder
                  │                             │
                  ▼                             ▼
         CasePromptBuilder            LessonPlanPromptBuilder
                  │                             │
                  └──────────────┬──────────────┘
                                 │
                                 ▼
                          Input Safety Guard
                                 │
                                 ▼
                             ModelClient
                                 │
                                 ▼
                         Output Safety Guard
                                 │
                                 ▼
                        ResponseFormatter
                                 │
                                 ▼
                              平台
```

**这才是比较适合你们当前项目的内部架构。**

最关键的三个边界是：

**第一，统一的是接口，不是业务逻辑。**
`/v1/chat/teaching` 统一入口，`chatType` 负责路由；案例导引和备课助手进入各自独立的 Handler、ContextBuilder 和 PromptBuilder。

**第二，复用的是“能力”，不是“业务流程”。**
两个业务可以共同使用 `ResourceQueryService`、`SafetyGuard`、`ModelClient`、`ResponseFormatter`，但资源“怎么选”、Context“怎么组”、Prompt“怎么写”必须分别处理。

**第三，静态资源接口只负责“查数据”，不负责“写 Prompt”。**
你的教材 JSON 已经天然适合做这一层：`entities.json` 提供教材、章节、节、知识点、教材原文、思政段落和标签，`relations.json` 提供它们之间的关联。 静态资源服务返回结构化 JSON，之后由不同业务的 ContextBuilder 和 PromptBuilder 分别组装成案例导引 Prompt 或教案 Prompt。

这样以后你真正开始写代码时，**第一步其实不是写 ****`/v1/chat/teaching`****，而是先把 ****`ResourceQueryService`**** 做出来**：让它能够根据 `schoolLevel + subject + textbookVersion + chapter + lesson + knowledgePoints`，从你现在这套 JSON 中稳定查出 `section → knowledge_points / textbook_chunks / curriculum_standards / ideology_paragraphs`。这个接口跑通后，再接两个业务 Handler，最后接模型和安全围栏，开发路径会非常清楚。
